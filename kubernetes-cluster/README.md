# Kubernetes Cluster Lab

A two-node Kubernetes cluster built manually using `kubeadm` on Ubuntu virtual machines running in VMware Workstation.

The lab covers Kubernetes cluster bootstrap, container runtime configuration, Pod networking, API server security, Ingress, application deployment, and Kubernetes networking troubleshooting.

Cluster Bootstrap
The control plane was initialized using kubeadm with:
sudo kubeadm init \
  --apiserver-cert-extra-sans=controlplane \
  --apiserver-advertise-address=192.168.178.110 \
  --pod-network-cidr=10.244.0.0/16 \
  --service-cidr=10.96.0.0/12
The API server advertises:
192.168.178.110:6443
After initialization, the generated kubeconfig was copied to the regular user's home directory so kubectl could manage the cluster.
The worker node was then added using the kubeadm join command generated by the control plane.
Bootstrap tokens and certificate hashes are intentionally not stored in this repository.

Container Runtime
containerd is used as the Kubernetes container runtime.
The runtime was configured with:
SystemdCgroup = true
to align containerd with the systemd cgroup driver used by Kubernetes.
The CRI plugins were verified before cluster initialization.

Kubernetes API Security
The Kubernetes API server listens on:
192.168.178.110:6443
UFW is enabled on the control-plane node.
API access is restricted to:
192.168.178.1     Windows management host
192.168.178.111   Kubernetes worker node
Example rules:
sudo ufw allow 22/tcp

sudo ufw allow from 192.168.178.1 \
  to any port 6443 proto tcp

sudo ufw allow from 192.168.178.111 \
  to any port 6443 proto tcp
Flannel VXLAN traffic is allowed on UDP port 8472.
Kubernetes Pod traffic is explicitly allowed through UFW routing:
sudo ufw route allow \
  from 10.244.0.0/16 \
  to 10.244.0.0/16
This preserves the default firewall policy while allowing Kubernetes networking to function.

Troubleshooting Highlights
CoreDNS timeout after enabling UFW
Pods on the worker node could access Service IPs but could not resolve Kubernetes DNS names.
Example:
nslookup juice-shop
connection timed out
The cause was UFW's default routed traffic policy:
deny (routed)
which blocked forwarded Pod traffic between nodes.
The issue was confirmed by temporarily disabling UFW and retesting DNS.
The final solution preserved UFW while explicitly allowing Kubernetes Pod routing and Flannel VXLAN traffic.
BusyBox networking test Pods exited immediately
Temporary BusyBox Pods entered:
Completed
because no long-running process was specified.
The Pods were recreated using:
sleep 3600
allowing kubectl exec, ping, and traceroute testing.
ingress-nginx remained in ContainerCreating
The ingress-nginx controller initially remained in ContainerCreating.
kubectl describe pod showed that the image pull required several minutes.
After the image successfully downloaded, the controller started normally.
This demonstrated the importance of using:
kubectl describe pod
kubectl get events
before assuming a Pod is stuck.
